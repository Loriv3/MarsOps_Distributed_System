MARSOPS // PROJECT // V1.0

PROJECT SCOPE
MarsOps is a distributed automation platform designed to guarantee the survival of occupants in a Martian habitat by integrating
heterogeneous IoT devices into a unified monitoring system. The platform acts as a bridge between a fragile habitat's infrastructure
and the human operators.
Operators can monitor critical environmental parameters in real-time through a centralized dashboard. They can, also, define
rules to ensure that habitat actuators respond instantly to dangerous environmental shifts without manual intervention.
By evaluating sensor data against operator-defined criteria, it triggers autonomous responses, such as activating cooling
systems or emergency ventilation, without requiring manual intervention, mitigating risks in high-latency Martian environments.

MARSOPS // CONVERTER-SERVICE // V1.0

CONVERTER SERVICE
The converter-service is the data ingestion and conversion layer of the MarsOps platform. It acts as a bridge between
heterogeneous IoT sources, which have different event formats and communicate in different forms (such as SSE and polling),
and the event queues that the other microservices attach to, ensuring that all other components operate on homogeneous and
similarly structured data.

By normalizing the way to receive data from sensors, it deduplicates the other complexity while removing it from all the
other microservices, ensuring that they can treat every source as basically identical as long as it provides the same “type” of metric
(for example temperature, pressure or air particle concentration).

MARSOPS // CONVERTER-SERVICE // V1.0

CACHE SERVICE
The cache service ensures that upon outages of the converter service, or whenever other microservices restart, they can
immediately query the system’s current state without waiting for update messages to appear on the internal event queue. It does so
by using Redis as an in-memory “ephemeral” cache, that however can still immediately provide the needed data.

This powers several parts of the system: for example, whenever the frontend connects for live updates, an initial batch of
synthesized updates is immediately sent to notify it of the state that it should display, in order to never display an empty dashboard.
Analogously, when the automation rules service starts, it can fetch the current state for all sensors and actuators so that it can know
which rules to skip as they have already run.

MARSOPS // CONVERTER-SERVICE // V1.0

METRICS SERVICE
The metrics service acts as middleware between the backend’s internal event queues and cache and a user or frontend that
might just want to receive live updates over more standard web browser protocols. For this reason, it exposes WebSockets for both
general updates, spanning all metrics, and more granular updates, for specific metric “group”, in order to avoid overloading a client
with information that it doesn’t care about.
As described in the previous slides, when a WebSocket is opened it first sends to it the currently cached state. This ensures that as
soon as clients request data, they receive a valid copy of it to display, while still getting live updates later.
Additionally, it enables discovery of all available metrics and their names and info by the frontend, making sure that it doesn’t have to
hardcode almost anything.

ACTUATOR SERVICE
The actuator service also acts as middleware between the backend’s internal event queues and cache and a user or frontend,
however this time that is relative to the actuators’ state and their updates. For this reason, in addition to the discovery features and
WebSockets for live state updates, it also provides POST endpoints to manually toggle actuators from the dashboard.
Like the metrics service, it also caches actuators’ state.

MARSOPS // CONVERTER-SERVICE // V1.0

AUTOMATION RULES SERVICE
The automation rules service maintains a core part of the system, by managing and persisting the automation rules that make
sure it correctly responds to specific situations detected by the sensors with the actuators it has available. For this reason, whenever
it receives updates from the sensor state queue, it evaluates them against all the rules it has stored and decides if a rule needs to be
fired. If so, it sends a message to the converter service to toggle the relevant actuator.
Internally, it uses SQLite to store automation rules, making sure that they don’t go lost even if the system goes down. Additionally, it
stores metadata about when the rules were fired, and why.
For a frontend, it provides a rich API to view, edit and delete all rules, as well as consulting the aforementioned logging data it has
collected; like the other services, it also provides a description of all this in a standardized OpenAPI format.
